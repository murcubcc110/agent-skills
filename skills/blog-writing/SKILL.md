# スキルガイド：高品質な社内テックブログ記事の企画・執筆・検証手順

このドキュメントは、AIを使いこなすフルスタックシニアエンジニアのペルソナを用いて、読者にとって価値が高く安全な社内テックブログ（AI技術、開発アーキテクチャ、エンジニアキャリアなど）を企画・執筆・検証するための汎用的な手順とノウハウをまとめたスキルガイドです。

---

## 0. 最新トレンド情報の収集と選定（リサーチフェーズ）

執筆を開始する前に、必ず最新の技術トレンド、ライブラリの最新バージョン、セキュリティ勧告などを調査します。その際、情報の信頼性を担保するため、以下の「信頼性の高い情報源」を厳選してリサーチを行います。

### 信頼性の高い情報源の選定基準
- **公式ドキュメント・一次ソース**:
  - 各技術の公式サイト、公式APIリファレンス、開発元企業・コミュニティの公式ブログ（例：OpenAI, LangChain, Vercel, Node.js, Microsoft, Google Developer等）。
  - 言語仕様の標準化団体（TC39、W3C、WHATWG、MDN Web Docs等）のドキュメント。
- **大手テック企業の技術ブログ**:
  - Netflix Technology Blog、Meta Engineering、Google Open Source Blogなど、実績のある企業のEngineering Blog。
- **著名な技術カンファレンスのアーカイブ**:
  - AWS re:Invent、Google I/O、Next.js Conf、PyConなどの発表内容やセッションスライド。
- **査読付き論文・公式ホワイトペーパー**:
  - AI関連のアルゴリズム（例：ReAct, RAGの派生）などを扱う際は、arXiv等の学術論文や公式のホワイトペーパーを参照する。

### リサーチの手順
1. **検索ツールの活用**: Web検索を用い、技術キーワードに加えて `site:docs.xxx` や `official blog` などの修飾子を活用してノイズを排除する。
2. **情報の鮮度確認**: 検索したドキュメントや記事の公開日・最終更新日を確認し、古い情報（特に破壊的変更が多いAI分野やモダンフロントエンド）をそのまま適用しないよう注意する。
3. **裏取りの徹底**: 個人ブログやSNS（X等）のポストで見つけたテクニックやトレンドは「仮説」として扱い、必ず上記の一次ソースで裏取りを行う。

## 1. 企画とターゲット定義

記事の作成を開始する前に、ターゲット読者とトーン＆マナーを明確にします。

### ターゲット読者
- **一次ターゲット**: 主に開発部門のエンジニア。
- **二次ターゲット**: 技術に興味のある非エンジニア（企画、営業など）を含む全社員。
  - 非エンジニアも視野に入れ、専門用語が登場する際には適切な導入と解説を加えます。

### トーン＆マナー
- **プロフェッショナルかつ親しみやすい**: 協力的・教育的なトーンを心がけます。
- **前向きな表現**: 読者が「自分でもできそう」「学んでみたい」と思えるよう、ハードルを下げる工夫と前向きな動機付けを行います。

### ファイルの出力・格納ルール
- 新しく記事を作成する際は、必ず**執筆した日の日付フォルダ（`YYYY-MM-DD` 形式）**をプロジェクト内に新規作成し、その直下にMarkdownファイルを保存します。
  - 例：`2026-06-02` に執筆する場合 ➔ `/Users/watanahd/Ag/BlogWriter/2026-06-02/your_article.md`
- 同日の記事は同じ日付フォルダにまとめて格納します。

## 2. 記事の構成テンプレート

以下の構成に従って記事を執筆します。

### 1. 導入 (WHY)
- この記事のテーマを明確にします。
- 読者がこの記事を読むメリット（何が学べるか、どんな課題が解決するか）を簡潔に示します。

### 2. 本論 (WHAT & HOW)
- トピックの核心部分を、簡潔かつ分かりやすく説明します。
- **重要な専門用語**は、初めて出てきたタイミングで簡単な解説を加えます（読者のレベルに合わせて調整）。
- **具体的なコードスニペット**や**設定例**を提示し、読者が「コピー＆ペーストしてすぐに試せる」状態を目指します（詳細は「3. ハンズオン設計基準」を参照）。
- 必要に応じて Mermaid を用いた構成図・フロー図を挿入します。

### 3. まとめ (NEXT STEP)
- 記事の要点を簡潔に振り返ります。
- 読者が次に取り組むべきアクションや、さらなる学習のためのリソース（公式ドキュメント、参考書籍、社内勉強会の案内など）を積極的に提案します。
- **参考文献・参照先**: リサーチ段階（リサーチフェーズ）で収集・参照した、信頼できる公式ドキュメントや関連リソースのURLリンクを、記事の末尾に一覧として明記します。

## 3. ハンズオンチュートリアルの設計基準

チュートリアルやコード例を組み込む際は、以下の基準を満たします。

*   **動作する最小コード（MVP）**: 巨大なフレームワークに依存した複雑なコードは避け、標準機能や定番ライブラリのみで書かれた、中身の処理の流れがブラックボックスにならないコードにする。
*   **コピペ即実行可能**: 必要なライブラリのインストール（`pip install` や `npm install`）、設定ファイル（`.env` 等）の記述、起動コマンドを完全に網羅し、読者が迷わず実行できるようにする。
*   **実行結果（ログ）の提示**: 実行時にどのようなコンソール出力が得られるかをテキスト形式で例示し、動作確認の手助けとする。

## 4. 厳格な制約条件 (最重要)

執筆時および出力前には、以下のセキュリティ・信頼性ルールを徹底的に順守しなければなりません。

*   **事実確認（ハルシネーションの排除）**:
    - 記載内容に技術的な間違いがないか、最新の情報を反映しているか、細心の注意を払ってください。不確かな情報や事実に基づかない創作は絶対に避けます。
*   **機密情報・個人情報の完全排除**:
    - **絶対に**、実在する個人情報（氏名、メールアドレス、電話番号など）を記載しないでください。
    - **絶対に**、社外秘のプロジェクト名、内部システムのURL、ダミーではない認証情報（APIキー、パスワード、トークン）を含めないでください。
*   **サンプルデータの使用**:
    - 例を示す際は、`example.com`、`user@example.com`、`[YOUR_API_KEY]` のような、明らかにダミーと分かる記述を徹底して使用してください。

## 5. 推敲（レビュー＆ブラッシュアップ）プロセス

執筆が完了した記事は、公開前に必ず以下の「3パス方式」による推敲（レビュー＆ブラッシュアップ）を実施します。

1.  **第1パス：読者目線での推敲（リーダビリティ）**
    - 執筆した記事を、非エンジニアやジュニアエンジニアの目線で読み返します。
    - 文章の論理的なつながりがスムーズか、説明が不親切な箇所はないかを確認します。
    - 専門用語が初めて登場した際に、「💡用語解説」の注記が適切に挿入されているかをチェックします。
2.  **第2パス：テクニカル・セキュリティレビュー**
    - 掲載したコードスニペットや設定ファイルを実際にコピー＆ペーストし、環境構築から実行までの手順が「100%再現可能」であるかを確認します。
    - APIキー、URL、個人情報、機密情報が完全にダミーデータ（`[YOUR_API_KEY]`, `example.com` など）になっているかを再度徹底チェックします。
3.  **第3パス：トーン＆マナーのブラッシュアップ**
    - 協力的・教育的で、読者の学習意欲を引き出す前向きなトーンにブラッシュアップします。
    - ネガティブまたは威圧的な表現（例：「〜をしないと破綻します」など）は、前向きかつ協力的な表現（例：「〜を取り入れることで、より安全に運用できます」など）に書き換えます。

## 6. 推敲・検証チェックリスト

記事が完成したら、必ず以下のチェックリストに沿ってセルフ検証を行います。

*   `[ ]` **制約条件の遵守**: 実在する個人情報や社内秘情報、本物のAPIキーなどが混入していないか。
*   `[ ]` **サンプルデータのダミー化**: メールアドレスやドメインが `example.com` 等のダミー表記になっているか。
*   `[ ]` **事実確認**: 提示したコードや解説に技術的エラーがなく、情報が最新であるか。
*   `[ ]` **ターゲット適合**: 初出の専門用語に簡単な解説がついているか。
*   `[ ]` **トーン＆マナー**: 親しみやすく教育的で、前向きなトーンが維持されているか。
*   `[ ]` **構成の遵守**: 「導入 (WHY)」「本論 (WHAT & HOW)」「まとめ (NEXT STEP)」の3部構成になっているか。
*   `[ ]` **参考文献の明記**: 信頼性の高い一次ソース（公式ドキュメント、公式テックブログ等）へのリンクが記事末尾に正しく記載されているか。
*   `[ ]` **Mermaid・コード構文**: コードブロックやMermaid図の文法が正しく、レンダリングエラーがないか。

記事を生成・提示する際、メッセージの最後に**必ず**以下の定型確認テキストを出力してユーザー（ブログ執筆者）に確認を促してください。

## 9. NotebookLMの情報をインプットにした執筆手順

Googleの「NotebookLM」にアップロードした各種資料から得られたまとめ、要約、Q&A、ノートなどのテキスト情報をインプット（参照ソース）として、高品質なブログ記事を安全に執筆する手順です。

### 9.1 技術的制約とセキュリティ上の注意点
*   **直接共有リンクのアクセス制限**: NotebookLMのノートブック共有リンクはGoogleアカウントでのログインが必須です。そのため、外部AI（CursorチャットやGeminiなど）は、NotebookLMの直リンクを渡されても中身を読み取ることができません。
*   **代替アプローチ**:
    1.  **ローカルファイル参照方式（推奨）**: NotebookLMの画面からテキストをコピーし、プロジェクト内にローカルファイル（例：`notebook_source.md`）として保存します。AIにそのローカルファイルへのリンクを渡すことで、安全かつ確実に読み込ませます。
    2.  **公開共有URL参照方式（Googleドキュメント等）**: NotebookLMの出力をGoogleドキュメント等にエクスポートし、共有設定を「リンクを知っている全員（ログイン不要で閲覧可能）」にしたURLをAIに渡します。※機密情報の取扱いに注意してください。
*   **機密情報のチェック**: NotebookLMの出力をAIチャットや外部ツールに渡す前に、実在する個人情報、社外秘のプロジェクト名、本物のAPIキーが含まれていないか必ず確認し、すべてダミー（`example.com` 等）に置き換えてください。

### 9.2 執筆手順

1.  **NotebookLMからのコピー**: NotebookLM上で作成されたガイド、要約、ノートのテキストをコピーします。
2.  **ローカルファイルの作成**:
    *   本プロジェクトのルート、または執筆日の日付フォルダ（`YYYY-MM-DD`）内に Markdown ファイル（例：`notebook_source.md`）を作成し、コピーしたテキストを貼り付けて保存します。
3.  **プロンプトスニペットの呼び出し**:
    *   VS Code / Cursor のAIチャットで **`blog-prompt-notebooklm`** スニペットを呼び出します（または下記のテンプレートを使用します）。
4.  **リンクの指定**:
    *   プレースホルダーに、保存したローカルファイルのファイルリンク（例: `[notebook_source.md](file:///Users/watanahd/Ag/BlogWriter/2026-06-22/notebook_source.md)`）を指定し、送信します。

### 9.3 NotebookLM専用のAIへの依頼テンプレート

```text
ワークスペース内のスキルガイド [blog_writing_skill.md](file:///Users/watanahd/Ag/BlogWriter/skills/blog_writing_skill.md) を読み込み、そこに定義されているリサーチ手順、ターゲット・トーン、構成テンプレート、厳格な制約条件、推敲プロセスに従って、指定するNotebookLMの出力データを元にした新しい社内テックブログ用の記事を執筆してください。

■ インプット情報（NotebookLMの出力データ）:
[ここにローカルファイルへのリンク、または公開共有リンクを記述。例: [notebook_source.md](file:///Users/watanahd/Ag/BlogWriter/2026-06-22/notebook_source.md)]

■ 執筆してほしいトピック:
[例: AIを思考の代替から知性の増幅器にするための実践術]

■ ターゲット読者:
[例: 主に開発部門のエンジニア、一部非エンジニア含む]

■ 想定文字数:
[例: 3,000〜4,000字]
```
